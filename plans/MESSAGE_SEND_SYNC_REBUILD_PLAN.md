# Message Send & Sync Rebuild Plan

Analysis date: 2026-09-14. Traced end-to-end across both repos (`SchneaggchatV3` client, `SchneaggchatV3server`). Supersedes the send-idempotency item of `OFFLINE_FIRST_ANALYSIS.md` (that doc's P0 item 3, "client-generated message ID for idempotency", is already implemented server- and client-side - this plan fixes what it didn't anticipate: a client-side race between the send path and the sync path). **Implemented** - see "File-by-file changes" for the actual diffs.

## TL;DR

`sendMessage()` / `sendOfflineMessages()` (outgoing) and `messageIdSync()` (incoming, driven by `dataSync()`) both write to the same local `messages` table, and `dataSync()` is triggered independently from ~10 places (map screen, events screen, group creation, settings changes, the friend-request socket handler, a 5s poll loop) with no awareness of an in-flight send. When an unrelated `dataSync()` pulled the very message a `sendMessage()` call was still waiting on a response for, the client used to create a **second** local row for it, because reconciliation was by server `id` only and the server never echoed `clientMessageId` back - so the incoming sync page carried nothing to match it against the still-pending row. That permanently orphaned the original pending row (`sent = false, id = null`), which in turn permanently blocked the offline-retry queue behind it.

An earlier version of this plan proposed fixing this by serializing sends against message-sync behind one shared lock. That works, but only by brute force - it doesn't fix the actual gap (missing correlation data), it just prevents the two operations from ever being in flight together, at the cost of a slow image/audio upload also delaying incoming message sync.

**What's actually implemented instead:** the server now echoes `clientMessageId` back, but *only* to the message's own sender (every other viewer still gets `null` - the field stays private). The client then reconciles incoming sync/socket messages by server `id` first, falling back to `clientMessageId` when no `id` match exists yet. This closes the race at its source instead of serializing around it - **sends and message-sync now run fully in parallel, exactly as before**, and can no longer produce a duplicate row no matter how they interleave.

## What already worked (no changes needed)

- Server send idempotency: `clientMessageId` (client-minted UUID) + unique partial Mongo index `{senderId, clientMessageId}` + `findByClientMessageId` short-circuit + `DuplicateKeyException` resolution (`MessageService.kt:64-226`, `Message.kt:16-30`). A retried send with the same `clientMessageId` always resolves to the same server document.
- Client `clientMessageId` minting/reuse: fresh `Uuid.random()` on first send, required reuse on resend (`AppRepository.kt:1719-1727`).
- `clientMessageId` already round-trips through the client's own domain/DTO layer (`chat/domain/Message.kt` `toDto`/`toMessage`, `MessageDto.kt`) - it just never had anywhere to be *matched against* on the incoming side until now.

## Root cause, hop by hop (as it was)

1. `sendMessage()` (`AppRepository.kt:1713`) inserts an optimistic local row (`sent=false, id=null, clientMessageId=C`), then awaits the server's HTTP response.
2. While that response is still in flight, something unrelated calls `AppRepository.dataSync(reason = ...)` - e.g. `SchneaggmapViewModel.kt:479`, `EventsViewModel.kt:284`, `GroupCreatorViewModel.kt:253`, `SocketConnectionMessage.kt:400`, any settings screen, or the 5s poll loop in `GlobalViewModel.kt`.
3. `dataSync()`'s `messageJob` calls `messageIdSync()` (`AppRepository.kt:2090`), which pages `/messages/sync`. The server's visibility query (`MessageLookupService.getMessagesSince`) includes the sender's **own** sent messages with no exclusion, so the message from step 1 - already committed server-side by the time this sync runs - comes back in the page.
4. `messageIdSync` reconciled purely by server `id`. No local row had that `id` yet (the pending row only had `clientMessageId`, which the server never echoed), so `existingLocalPK` defaulted to `0`, and Room autogenerated a **brand-new** row.
5. Step 1's `sendMessage()` call eventually got its response and reconciled by `id` too - it found the row `messageIdSync` had just created and updated *that* one. The original pending row from step 1 was never touched again: `sent=false, id=null` forever.
6. `sendOfflineMessages` (`AppRepository.kt:1984-2079`) always retries `getUnsentMessages().first()` and stops the whole drain as soon as that same row is still the head after an attempt - the orphan from step 5 was always "unchanged" (the server just dedups it every time via `clientMessageId`), so it permanently blocked every other queued message, in every chat, forever.

## Design actually implemented

### 1. Server: echo `clientMessageId` back, sender-only

`Message.toMessageResponse(requestingUserId)` (`Message.kt:104-126`) already takes the id of whoever is asking - every call site already passes the right one (`MessageController`'s direct send/edit/react responses, `MessageService.messageSync`'s `requestingUser`, `NotificationService`'s per-recipient socket fan-out). One line added:

```kotlin
clientMessageId = if (this.senderId == requestingUserId) this.clientMessageId else null,
```

- `/messages/sync`: `requestingUser` is the syncing user themselves, so their own sent messages now carry their `clientMessageId` back; everyone else's messages still carry `null`.
- Socket `MessageChange` pushes: harmless no-op in practice today, since `notifyMessageUpdate` already excludes the sender (`changingUserId`) from ever receiving their own message's push (group and single-message branches both skip them) - so `requestingUserId == senderId` is never true on a push a client actually receives. Added anyway for symmetry, in case that exclusion ever changes.
- `MessageResponse` (`MessageResponse.kt`) gained the field; client's mirrored `NetworkUtils.MessageResponse` gained it too.
- No index, schema, or validation changes - `clientMessageId` was already stored and queryable server-side.

### 2. Client: reconcile by `id`, fall back to `clientMessageId`

- `MessageDto.kt`: added a unique index on `clientMessageId` (safe despite nullability - SQLite treats every `NULL` as distinct in a unique index).
- `Daos.kt`: added `getMessageDtosByClientMessageIds(ids: List<String>)`, batch-queried the same way `getMessageDtosByIds` already is.
- `MessageRepository.kt`: added the chunked wrapper `getMessageDtosByClientMessageIds` and a single-item `getMessageByClientMessageId` for the socket handler.
- `AppRepository.messageIdSync` (`:2090`): after the existing by-`id` batch lookup, do a second batch lookup by `clientMessageId` for whichever updates in the page didn't match by `id` and carry one, then prefer that match. One extra query per sync page, only ever populated for the syncing user's own messages.
- `SocketConnectionMessage.kt`'s `MessageChange` handler: same fallback, single-item.

Net effect: a sync/socket pull that sees "my own message, no local row has this `id` yet" no longer assumes it's brand new - it checks whether a still-pending row with this `clientMessageId` exists and, if so, updates that row in place (setting its `id`, `sent = true`, etc.) instead of inserting a second row. When the original `sendMessage()` call's own response arrives afterward, it finds that same row by `id` (now already merged) and updates it again in place - one row, either order, no lock required.

### 3. Widen "server rejected it -> delete locally" beyond `BadRequest`

`AppRepository.kt`, the `NetworkResult.Error` branch of `sendMessage`:

```kotlin
if (error is NetworkingError.BadRequest || error is NetworkingError.Conflict) {
    database.messageDao().deleteMessageDtoByPk(localpkintern)
}
```

- `BadRequest` (400) = validation failure (bad text/poll/image) - unchanged, already deleted before.
- `Conflict` (409) = added for forward safety. Not returned by the server today - the `DuplicateKeyException` catch in `MessageService.kt:209-212` only fails to resolve if `findByClientMessageId` still returns nothing after the exception, which isn't reachable in practice (would require generating the same UUID twice), and currently falls through to a generic 500 instead, which already stays queued correctly. Left server-side as-is; not worth a change for an unreachable case.
- Everything else stays queued for retry: `NetworkTimeout`, `NoInternetConnection`, `ServerError`, `TooManyRequests` are transient; `Unauthorized`/`Forbidden`/`NotFound`/`PayloadTooLarge`/`SerializationError`/`Unknown` are ambiguous enough that silently deleting the user's message would be the wrong call (e.g. `Forbidden` could mean "removed from the group" mid-queue - the user should see a failed-send marker, not have the message vanish).

## What did NOT change

- No locking changes anywhere - `sendMessageLock`, `sendOfflineLock`, `dataSyncLock` are untouched, and `messageIdSync` still runs fully concurrently with sends inside `dataSync`'s `coroutineScope`, same as every other sync job. This was the whole point: fixing the missing correlation key meant no new lock was needed at all.
- `clientMessageId` minting/reuse logic on the client - unchanged, already correct.
- `dataSync()`'s overall job structure/UI status reporting - untouched.
- Reactions, edits, deletes, read receipts, polls - out of scope for this pass.

## Testing checklist

- Send a message and, before its response returns, trigger `dataSync` from an unrelated screen (e.g. open the map) - confirm no duplicate row appears, and confirm every `dataSync` job (including MESSAGES) still runs concurrently with the send, not queued behind it.
- Force a `BadRequest` (e.g. oversized poll payload) - confirm the local row is deleted, not left stuck.
- Force a `Conflict` (can't currently be triggered server-side - inspect manually or stub the response) - confirm the local row is deleted.
- Queue two offline messages, reconnect while a background sync is also running - confirm both send, no duplicates, no interleaving corruption.
- Confirm a normal (non-racing) send and a normal sync both still work unchanged - the fallback path should only ever activate when the `id`-based lookup misses.
