- [ ] **M** **no code** **Important: too many unclear socket disconnects on the server.** The server log and admin page show many closes without a clear reason. While a socket is silent, the server still treats the user as online for up to 75 s (30 s ping, 2.5x pong timeout) before its keepalive sweep closes it, so pushes for that time can go to a dead socket. User, 2026-10-30: server-side logging for this was just added; deploy it, then check whether it still happens and which cause dominates. Client cases still open after the desktop quit fix (branch `desktopsocketclose`): desktop system sleep keeps the socket open until the server sweep (a `java.awt.desktop.SystemSleepListener` could close it on sleep and reconnect on wake); macOS Cmd+Q, logout and shutdown do not pass through `quit()` in `jvmMain/…/main.kt` (needs `Desktop.setQuitHandler`); a network switch or loss leaves the old socket silent on the server (client reconnects after the 20 s OkHttp ping, `C/datasource/network/createHttpClient.kt:139`). - [ ] **M** **A push is skipped when its message is already stored** (`androidMain/…/utilities/notifications/AppFirebaseMessagingService.kt:137-142`). "Mark as read" and "Reply" on a notification run `setAllChatMessagesRead`, which runs `syncMessages()` (`C/chat/data/OfflineFirstMessageRepository.kt:964`) in the background. That sync stores new messages of other chats before their pushes arrive, so those pushes are dropped and the user is never notified. Same after any sync while the socket is down. Proposed: skip only ids this process already notified (in-memory registry claimed by the socket path and the push path) plus a dedupe of identical messages in `AndroidNotifier.showMessageNotification`. User, 2026-10-21: done together with the server-side notification refactor (see `plans/DEVICE_AWARE_PUSH_PLAN.md`). *(Android push audit 2026-10-21)*
