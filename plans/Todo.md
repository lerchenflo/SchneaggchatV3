## Findings from migration Phase 4.5 (2026-10-14)

Noticed while writing the send-path characterization tests (`composeApp/src/jvmTest/.../chat/data/MessageSendTest.kt`, `MessageSendEchoDedupTest.kt`, `OfflineMessageQueueTest.kt`). The tests pin today's behavior, including these. Not fixed; input for the message-sending rebuild.

- [ ] **One message that keeps failing blocks the whole offline queue.** `sendOfflineMessages` stops as soon as the head row is still unsent after an attempt (`C/datasource/AppRepository.kt:1009-1010`). - [ ] `MessageDao.getUnsentMessages()` (`C/datasource/database/Daos.kt:361`) has no `ORDER BY`. The offline queue's oldest-first order only holds because SQLite happens to walk the `sent` index in rowid order. Add `ORDER BY localPK` (or `sendDate`).

Harmless today, because the row has its server id by then, but the idempotency key is gone from the local copy. Pinned by `MessageSendTest` / `MessageSendEchoDedupTest`; update them if the rebuild keeps the key.
- [ ] `sendOfflineMessages`, AUDIO branch (`C/datasource/AppRepository.kt:987-989`): the `if (m.audioPath == null) { TextContent("Offline audio sending failed") }` result is thrown away, so it always goes on to read the audio file. - [ ] Every failed attempt pushes an `ErrorEvent` popup (`C/datasource/AppRepository.kt:845`), including each offline-queue retry. A row that keeps failing shows the same popup on every resume / reconnect.
- [ ] Edge case: a `BadRequest` / `Conflict` response deletes the row by local PK (`C/datasource/AppRepository.kt:840-842`) even when a parallel sync already merged the server copy into that row (sync before the send response).
